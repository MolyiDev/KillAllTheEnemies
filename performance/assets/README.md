# BoneGrid: one skinned mesh, many independently-driven elements

`BoneGrid100.fbx` / `.glb` - a single skinned mesh containing **100 cubes, each bound to its own bone** at
weight 1.0 with no blending between them. Generated by [`make_bonegrid.py`](make_bonegrid.py)
(`blender --background --python make_bonegrid.py`).

## What it is for

The measured ceiling for skinned meshes is **~4800 instances** ([09](../09-skinned-ceiling.md)), while a bone
write costs **79ns** ([02](../02-bone-vs-motor6d.md)). Those two facts together suggest the binding constraint is
the number of **MeshParts**, not the number of things moving.

If that is right, packing 100 entities into one mesh turns 4800 instances into **48**, and the ceiling should
move by roughly two orders of magnitude while keeping everything bones already win at (movement, colour,
animation, spawn cost).

## Construction, and why each choice matters

- **All 100 cubes are centred on the origin and overlap at rest.** A vertex is displaced by its bone's Transform
  applied about the bone's rest, so geometry centred on the bone's rest origin means
  `bone.Transform = <world CFrame>` places that element exactly there - the same mapping Ballarc's
  `EnemiesController` relies on. Give a cube a rest position away from its bone and the Transform would orbit it
  instead of placing it.
- **Every bone sits at the origin with an identity rest** (head `(0,0,0)`, tail `(0,1,0)`, roll 0). In Blender a
  bone's local +Y runs head to tail, so this is the one orientation whose rest matrix is identity. Anything else
  bakes a rotation into the mapping above.
- **Cubes, not planes.** A plane has a facing direction and Blender's Z-up to FBX Y-up conversion makes it hard
  to predict which way it ends up pointing in Roblox. A cube reads from every angle, and it matches the existing
  `Test` / `Skeleton` geometry so the benchmark stays like-for-like.
- 2 Blender units per cube, so ~2 studs on import - same as the `Test` mesh.

## Importing

Open Cloud asset upload does not support mesh types, so this needs Studio's importer:

1. **File > Import 3D** (or the Avatar tab's 3D Importer), pick `BoneGrid100.fbx`.
2. Leave the rig/skinning options at their defaults - the importer detects the armature and produces a MeshPart
   with 100 `Bone` children.
3. Check the scale reads about 2 studs. Adjust the importer's scale if not.
4. Put the result in **`ReplicatedStorage.Models`** named **`BoneGrid`** so the benchmark can find it.

Expect the preview to look like a single cube: the 100 cubes are stacked on the origin at rest, by design. They
only separate once bone Transforms are written.

If the import produces something unexpected, `BoneGrid100.glb` is the same asset in glTF, which Roblox also
accepts and which carries skinning more predictably than FBX.

## Known risk

With all geometry at the origin at rest, the MeshPart's bounding box is one cube. Whether Roblox culls the
displaced skinned geometry against that box is untested - if elements vanish when they should be visible, that
is the cause, and the fix is to regenerate with spread-out rest positions and drive bones by offset-from-rest
instead of absolute world CFrame.
